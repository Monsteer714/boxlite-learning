# Analysis: BoxLite infra — network model

## Key Entities

| Entity | Type | Role in Source | In Wiki? |
|---|---|---|---|
| **BoxLite Control Plane** | AWS infrastructure deployment | **Central** — this document is the network-model rationale for the control-plane VPC (`sst.config.ts` §2 + §10) | Yes — [[entities/boxlite-control-plane\|BoxLite Control Plane]]; this source substantially extends it |
| **EC2 Runner** | Compute host in public subnet | **Central** — the host that actually runs BoxLite; has an egress-only public IP, SG pinned to `:3003` from VPC CIDR only | No — should be captured as a component of the control plane |
| **NAT instances (fck-nat, t4g.nano)** | Instance-based NAT appliances | **Central** — per-AZ egress for all private tasks; the cost/HA/fail-closed discussion revolves around them | No |
| **Application Load Balancer (ALB)** | AWS load balancer | **Central** — the *only* inbound door to the VPC | No |
| **Internet Gateway (IGW)** | AWS gateway | **Central** — the single path both inbound and outbound | No |
| **Security Groups (SG)** | AWS firewall primitive | **Central** — the sole inbound control surface for the runner (pattern B); a full layer for private tasks (pattern A) | No |
| **SST (`sst.config.ts`)** | Infrastructure-as-code framework | Peripheral but cited as source of truth (§2 PLATFORM, §10 RUNNER) | No |
| **Fargate tasks (Api, Proxy, Otel, Jaeger, MailDev, PgAdmin)** | Containerized services in private subnets | Peripheral — the consumers of the egress model; Api/Proxy are the primary workloads | No (could fold into control-plane page) |
| **Postgres, Redis** | Data stores in private subnets | Peripheral — hold user data/secrets; the stated reason services get the fail-closed pattern | No |
| **ghcr.io, ECR** | OCI image registries | Peripheral — egress destinations for image pulls; the *reason* the runner needs high-bandwidth direct egress | Related: [[concepts/oci-image\|OCI Image]] |
| **Auth0, ClickHouse** | Identity provider / analytics store | Peripheral — egress destinations revealing control-plane dependencies (auth, telemetry) | No |

## Key Concepts

| Concept | Definition | Why It Matters | In Wiki? |
|---|---|---|---|
| **Two egress patterns (fail-closed vs fail-open)** | A: private subnet + NAT → no inbound route + SG (2 layers, fail-closed — internet has *no path*). B: public subnet + public IP + SG → internet *has* a path, SG is the only gate (1 layer, fail-open) | The central design decision: services use A; the runner is forced to B by EC2/high-bandwidth egress needs | No — worth a concept page |
