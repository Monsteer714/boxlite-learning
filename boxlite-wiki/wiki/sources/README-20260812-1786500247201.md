## Key Concepts

- **Dual-use-only design principle** — Only include code genuinely used by *both* host and guest. Side-specific code stays in its respective crate. This is the crate's governing philosophy and the source of its deliberately minimal scope.
- **Channel configuration (`ChannelConfig`)** — Enum abstracting TCP, Unix socket, and Vsock transports with URI parsing (`tcp://`, `unix://`, `vsock://`). Notable: it's the *shared* type for connection setup — host side "connects," guest side "listens." This is the configuration surface beneath the Portal/gRPC communication layer.
- **Shared error handling** — `CoreError` plus the `Result<T>` alias, giving both sides a common error vocabulary.

## Main Arguments & Findings

- **Claim**: The crate is intentionally minimal — only genuinely shared code, nothing host-only, guest-only, or platform-specific unless used by both sides.
- **Evidence**: The README's explicit "What NOT to include" section and the stated design principle. This is a design-governance document, not an empirical report — evidence is prescriptive, not measured.
- **Strength**: Weak as evidence (it's a policy statement), but clear as a specification of crate boundaries.
